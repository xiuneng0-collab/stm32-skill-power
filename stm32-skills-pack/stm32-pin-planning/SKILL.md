# STM32 Pin Planning

这份 skill 只处理一件事：把 STM32 项目的“真实占脚情况”搞清楚，不被配置文件和想当然误导。

## 默认立场

做引脚整理时，默认遵守这几个判断：

1. 配置文件不是唯一真相。
2. 自动生成配置不是最终真相。
3. 真正的占脚情况，要以实际源码路径和板级连接为准。
4. 一个外设“被配置了”不等于它“真的占用了外部引脚”。
5. 一个外设“没在配置文件里”也不等于它“没有被后续源码手工补上”。

## 先查哪些地方

默认按下面顺序交叉核对：

1. 配置文件
- `.ioc`
- 板级配置表
- 生成器输出

2. GPIO 初始化
- `gpio` 初始化文件
- MSP 初始化
- 时钟使能

3. 外设初始化源码
- UART / SPI / I2C / ADC / TIM / PWM / DMA / 存储 / USB 等外设源码
- 是否有手工追加通道、总线宽度、片选、触发脚、诊断脚

4. 板级头文件与宏定义
- 板级别名
- LED / KEY / CS / EN / RESET / INT 等宏

5. 板子连接事实
- 原理图
- 接口定义
- 排针说明
- 模块连接说明

## 输出时要区分的四类引脚

整理时必须明确区分：

### 1. 真实外部占脚

真正连到外设、接口、传感器、连接器或板级功能的脚。

### 2. 内部功能脚

例如只作为内部触发、内部定时、内部事件链的一部分，但不需要外部接线的脚。

### 3. 保留 / 调试 / 系统脚

例如调试口、复位脚、时钟相关脚，必须单独列出，不能混在普通 IO 里。

### 4. 名义配置但实际未用

配置里有，源码里没启动，或者只是占位，没有形成真实链路的脚。

## 默认排查顺序

### 1. 先确认用户要的是什么

可能是：

- 画引脚分配图
- 整理引脚表
- 查冲突
- 核对某个外设到底用哪几个脚
- 判断某个引脚还能不能复用

先分清任务类型，再决定整理深度。

### 2. 先从外设反推引脚，不从引脚正推外设

更稳的方式通常是：

- 先列外设
- 再列每个外设实际使用的引脚
- 再汇总成总表

不要一上来扫所有引脚，这样很容易混入无关配置。

### 3. 发现冲突时先判断哪种冲突

常见冲突有：

- 两个外设抢同一引脚
- 调试口和普通 IO 冲突
- 板级功能和外设复用冲突
- 自动生成配置和手工改动冲突
- 原理图连线与软件假设冲突

## 什么时候不能只信配置文件

遇到这些情况，默认不能只信 `.ioc` 或类似配置：

- ADC、SPI、SDIO、USB、DMA 这类经常会被手工扩展
- 代码里出现多个初始化入口
- 板级头文件有很多自定义宏
- 外设支持多种总线宽度、多个通道、多个模式
- 用户明确说“配置文件没更新”

## 整理真实占脚时的默认格式

输出建议按外设分组，而不是按端口字母堆列表。

推荐字段：

- 外设名
- 引脚
- 功能
- 是否真实外部占用
- 证据来源
- 是否有冲突或疑点

如果用户想看总表，再补一份按引脚排序的视图。

## 常见场景的默认策略

### 画引脚分配图

- 先做文本表
- 再做图
- 图必须基于最终核对后的表，不要直接从配置文件自动翻译

### 查某个外设到底用哪几个脚

- 先看配置
- 再看 MSP
- 再看外设初始化源码
- 再看板级宏
- 最后看原理图或说明

### 查某个引脚还能不能复用

先确认：

- 当前是否已被真实占用
- 是否是调试口或系统脚
- 是否只是名义配置未实际使用
- 是否和另一个外设形成硬冲突

### 查代码与原理图不一致

- 不要先改原理图结论
- 先确认是不是代码手工扩过
- 再确认是不是原理图版本不一致
- 再确认是不是板级宏和配置文件脱节

## 明确指出的内容

做 pin planning 时，默认要显式指出：

- 哪些脚是已确认占用
- 哪些脚只是推测
- 哪些脚有冲突
- 哪些脚是内部功能，不需外接
- 哪些脚是调试或系统保留

不要把不确定项写成确定项。

## 输出模板

处理 STM32 引脚任务时，尽量按这个顺序输出：

### 已确认占脚

- 哪些外设真实占用了哪些脚

### 仅配置未证实

- 哪些脚只是配置里出现，还没证据证明真实使用

### 冲突与风险

- 哪些脚存在复用冲突、调试冲突或板级冲突

### 建议的下一步核对

- 还要补看哪些源码、头文件、原理图或连接说明

## 不要做什么

- 不要把 `.ioc` 当最终结果
- 不要只看 `gpio.c`
- 不要漏掉 MSP 和板级宏
- 不要把内部触发脚当成外部接线脚
- 不要把推测写成定论
- 不要静默忽略冲突
