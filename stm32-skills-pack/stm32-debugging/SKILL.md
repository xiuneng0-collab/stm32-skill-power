# STM32 Debugging

这份 skill 只做一件事：快速把 STM32 问题缩到正确层级，不靠大面积试错。

## 先做什么

默认先做下面四件事：

1. 先确定症状，不急着改代码。
2. 先确定问题发生在什么时候。
3. 先确定哪条链路最可疑。
4. 先补最小观测点，再决定修什么。

不要一上来就：

- 重写驱动
- 换架构
- 大改初始化
- 同时改多个外设
- 靠感觉降规格

## 先给问题分型

先把问题归入下面某一类：

### 1. 上电后完全不跑

优先怀疑：

- 启动文件
- 时钟初始化
- 死循环卡在早期初始化
- 看门狗或异常复位
- 调试口不可用

### 2. 能跑，但某个外设完全没反应

优先怀疑：

- GPIO 复用不对
- 外设时钟没开
- 初始化函数没执行
- 启动调用没执行
- 外设被别的资源占用

### 3. 有中断配置，但就是不进中断

优先怀疑：

- NVIC 没开
- 中断源本身没触发
- 标志位没置位
- 中断函数名不匹配
- 向量表或条件编译有偏差

### 4. DMA 配了，但数据不对或回调不对

优先怀疑：

- 源/目标地址
- 数据宽度
- 长度和边界
- 普通模式 / 循环模式
- 回调时机
- 缓冲区被覆盖

### 5. 串口能发不能收，或能收不能发

优先怀疑：

- TX/RX 引脚复用
- 波特率与时钟
- 中断接收链
- 轮询接收逻辑
- 缓冲区和状态机

### 6. ADC、PWM、定时器数值不对

优先怀疑：

- 时钟源和分频
- 触发源
- 通道映射
- 对齐方式
- 采样时间
- 自动重装和计数计算

### 7. 工程运行一段时间后才卡

优先怀疑：

- 缓冲区越界
- 内存耗尽
- 中断风暴
- 外设忙等待
- 状态机进了不可恢复分支
- 存储或通信链路阻塞

## 先问清楚的四个问题

如果信息不够，优先补齐这四个判断：

1. 之前有没有工作过
2. 是一直不工作，还是改完后不工作
3. 是启动就坏，还是运行后坏
4. 坏的是“完全没反应”，还是“有反应但数据不对”

这四个问题能直接决定排查顺序。

## 标准排查顺序

默认按这个顺序缩小范围：

### 1. 入口是否真的执行

- `main` 是否进来
- 外设初始化是否真的调用
- 启动调用是否真的执行
- 是否卡在某个 `while`、等待、超时或错误分支

### 2. 时钟是否可信

- 系统时钟是否按预期
- 外设总线频率是否按预期
- 定时器、串口、ADC 的计算是否仍然成立

### 3. 引脚是否可信

- 引脚是否真的是那个功能
- 板级连接是否和源码一致
- 是否与调试口、别的外设、板级功能冲突

### 4. 初始化顺序是否合理

- GPIO
- 外设时钟
- DMA
- 中断
- 外设启动

如果顺序错了，后面所有现象都可能是假的。

### 5. 中断 / DMA 链是否连通

- 源头有没有事件
- 中断有没有进
- 回调有没有跑
- DMA 有没有真的搬
- 回调里看到的数据是不是本轮数据

### 6. 缓冲区是否安全

- 长度
- 对齐
- 越界
- 所有权
- 是否被多个上下文同时写

### 7. 观测点是否足够

如果还不能确定问题，就先补一个最小观测点：

- 一个 GPIO 翻转
- 一条短串口日志
- 一个计数器
- 一个状态码
- 一个关键变量快照

不要在没有观测点时继续扩大修改。

## 对不同外设的默认怀疑点

### GPIO

- 模式不对
- 上拉下拉不对
- 端口时钟没开

### UART

- 波特率依赖的时钟错了
- RX/TX 接反或复用错
- 中断接收链漏了一环

### SPI / I2C

- 时钟极性相位
- 速率过高
- 片选时序
- ACK / 忙标志处理

### ADC

- 通道错
- 采样时间太短
- 触发源没工作
- 数据对齐理解错

### Timer / PWM

- 分频和重装计算错
- 时钟源理解错
- 通道没启动

### DMA

- 地址、长度、模式不一致
- 回调和缓冲区预期不一致

## 最小修复原则

默认只接受这种修复方式：

- 能说明为什么改
- 改动层数少
- 容易回退
- 改完能立刻验证

默认不接受这种修复方式：

- 一次改三四个外设
- 顺手重构
- 把旧逻辑整块推翻
- 因为“看起来更合理”就换架构

## 输出模板

处理 STM32 调试任务时，尽量按这个顺序输出：

### 当前症状

- 精确描述用户看到的现象

### 最可能的问题层

- 启动 / 时钟 / 引脚 / 初始化 / 中断 / DMA / 缓冲区 / 通信 / 存储

### 先验证什么

- 下一步最小、最快、最有区分度的检查

### 如果验证通过

- 说明什么

### 如果验证失败

- 下一层该查什么

## 不要做什么

- 不要把“无输出”直接等同于“主循环没跑”
- 不要把“中断没进”直接等同于“NIVC 没开”
- 不要把“数据不对”直接等同于“算法错了”
- 不要因为着急而同时改时钟、引脚、DMA、逻辑
- 不要没有观测点就重构
