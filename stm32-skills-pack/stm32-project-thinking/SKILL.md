# STM32 Project Thinking

先把 STM32 任务做对，再把它做漂亮。

这份 skill 的目标不是提供某个芯片或某个库的专有知识，而是约束工作方式，让 Codex 在基础 STM32 项目里少走弯路、少盲改、少复杂化。

## 默认工作方式

收到 STM32 任务后，默认按下面的顺序行动：

1. 先做只读摸底，再决定是否改代码。
2. 先列出已确认事实，再列出仍是猜测的地方。
3. 先说清目标和不变量，再讨论修改方案。
4. 先分层定位问题，再挑最小改动点。
5. 先证明问题在哪一层，再决定是否需要更大改动。

默认心态：

- 真正的根因，通常比第一眼想象的更基础。
- 硬件连接、时钟、引脚复用、初始化顺序、中断链、DMA 链、缓冲区边界，往往比业务逻辑更值得优先怀疑。
- 目录名、文件名、旧注释、自动生成配置都只能算证据，不能算事实。
- 没验证前不要相信“应该是这样”。

## 核心原则

始终遵守这些原则：

1. 先确认真实事实，再相信名字、注释、工具配置或口头描述。
2. 先分层，再动手：应用逻辑、状态机、外设驱动、板级连接、芯片资源、构建配置、工具链。
3. 先找不变量，再找适配点，避免把已验证功能和新问题混改。
4. 先缩小问题范围，再修改代码，不允许大面积试错。
5. 先用最小改动跑通，再谈重构、抽象和优化。
6. 先怀疑基础链路，再怀疑高层逻辑。
7. 每次准备复杂化前，先判断这是不是根因，还是只是给系统加层。
8. 默认优先简单、稳定、可回退、可验证的方案。

## 标准分析顺序

除非有明确理由，否则按这个顺序分析：

### 1. 目标与边界

- 用户想达到什么结果
- 当前哪些功能已经工作
- 哪些行为必须保持不变
- 哪些变化是允许的

### 2. 工程真实入口

- 启动文件
- `main` 或主任务入口
- 外设初始化入口
- 中断入口
- 构建入口
- 板级头文件、宏定义、条件编译

### 3. 时钟与启动

- 系统时钟来源
- 外设总线频率
- 定时器频率假设
- 延时、超时、采样率、波特率是否依赖时钟
- 是否存在“配置改了但计算公式没跟着变”的情况

### 4. GPIO 与引脚复用

- 真实使用的是哪些引脚
- 引脚功能是否和源码一致
- 是否和调试口、其他外设、板级功能冲突
- 自动生成配置与手工修改是否一致

### 5. 外设初始化顺序

- GPIO 是否先于外设使能
- DMA 是否先于外设启动
- 中断是否在错误的时机打开
- 某个外设是否依赖另一个外设先完成初始化

### 6. 中断与 DMA 链路

- 中断是否真的进入
- 回调是否真的执行
- DMA 是否真的搬到预期地址
- 长度、对齐、模式、所有权是否正确
- 是否存在重复启动、漏清标志、双重回调、竞争访问

### 7. 缓冲区与内存使用

- 全局缓冲区大小是否合理
- 栈和堆是否吃紧
- 环形缓冲、双缓冲、线性缓冲是否边界正确
- 是否存在越界、覆盖、未初始化、对齐错误

### 8. 通信或存储全链路

- 数据从哪里产生
- 中间经过哪些缓冲
- 最终由谁消费
- 出错后如何处理
- 如果是存储链路，是否区分“初始化成功”和“真正写成功”

### 9. 观测点

在大改之前，先补最小观测点：

- 状态灯
- 简短串口打印
- 计数器
- 状态变量快照
- 边界检查
- 错误码

### 10. 最小修复

只有在链路看清楚之后，才选择最小、最稳、最容易验证的修复方案。

## 常见任务的默认策略

### 新工程 Bring-Up

- 先确认上电、启动、时钟和一个最小活性信号。
- 先点灯，再串口，再单个外设，不要一次性全开。
- 自动生成代码只是起点，不是最终真相。

### 外设不工作

默认先查：

1. 引脚是否真的对
2. 时钟是否真的开
3. 初始化是否真的执行
4. 外设是否真的启动
5. 中断或 DMA 是否真的连通
6. 是否被别的资源抢占

不要从“没有数据”直接跳到“重写驱动”。

### 死机 / 卡住 / 无输出

默认先分清：

- 卡在启动前
- 卡在初始化过程中
- 初始化后主循环不动
- 运行一段时间后才卡
- 只在中断、DMA、存储、通信事件后卡

然后继续区分：

- CPU 卡死
- 死循环等待标志
- 中断风暴
- 外设一直忙
- 数据链路堵塞

### 引脚分配整理

- 不只看配置文件。
- 交叉核对配置文件、GPIO 初始化、MSP、外设源码、板级头文件。
- 以当前真实代码路径为准。
- 明确指出冲突、保留脚、内部触发脚、调试口占用。

### 串口 / SPI / I2C / ADC / PWM / 定时器调试

默认检查顺序：

1. 时钟
2. 引脚复用
3. 初始化顺序
4. 启动调用
5. 中断或 DMA
6. 测量方式

例如 ADC 数值不对时，先查参考电压、采样时间、触发源、通道映射和数据对齐，不要先改算法。

### 简单存储与缓存判断

做存储或缓存判断时，先回答：

- 需要多大容量
- 是顺序访问还是随机访问
- 对时延敏不敏感
- 断电后要不要保留
- 是配置保存还是数据缓存

默认选择满足需求的最简单方案，不为了“高级感”引入更复杂存储。

### 旧工程迁移到新板

- 先提取已验证行为。
- 先分离业务层和板级适配层。
- 先保行为一致，再保结构整齐。
- 把时钟、引脚、内存映射、中断、外设连接、胶水层都当成适配层。
- 除非必须，不要把“移植”和“功能升级”绑在一起做。

### 性能与功耗取舍

- 先问清楚优先级：正确性、实时性、吞吐量、功耗，谁排第一。
- 没有测量就不要断言优化有效。
- 不要拿不稳定换理论性能。
- 不要拿不可验证的省电技巧换可维护性。

## 按症状分流

如果用户的问题本身很模糊，先按症状分流：

### 上电后完全不跑

优先查：

- 启动文件
- 时钟
- 复位状态
- 调试口是否可连
- 最早期 GPIO/串口观测点

### 能运行但外设没反应

优先查：

- GPIO 复用
- 外设时钟
- 初始化是否被调用
- 启动调用是否执行

### 有中断配置但进不来

优先查：

- NVIC 开启
- 中断源是否真的产生
- 标志位是否设置
- 处理函数名字是否匹配
- 向量表是否正确

### DMA 配了但数据不对

优先查：

- 源地址和目标地址
- 长度和数据宽度
- 循环 / 普通模式
- 缓冲区越界
- 回调时序

### 串口能发不能收

优先查：

- RX 引脚复用
- 中断或轮询路径
- 缓冲区覆盖
- 接收状态机
- 波特率和采样时钟

### 工程迁移后编译过了但功能不对

优先查：

- 时钟假设是否变了
- 引脚映射是否变了
- 板级宏定义是否还沿用旧板
- 存储基地址、外设实例、中断号是否变化
- 中间层是否还是旧平台定制版本

## 输出模板

处理 STM32 任务时，尽量按这个顺序汇报：

### 已确认事实

- 从代码、配置、观测现象里确认了什么

### 当前目标与不变量

- 用户要什么
- 什么不能退化

### 最可能的问题层

- 现在最值得怀疑的是哪一层

### 最小修改路径

- 下一步最小、最安全、信息量最大的动作是什么

### 验证步骤

- 改完后看什么
- 什么结果说明判断对了
- 什么结果说明要换方向

默认保持简洁，不做长篇文件流水账。

## 基础场景基准

这份 skill 的例子和默认思路，只围绕最基础场景：

- GPIO 点灯
- 按键输入
- 串口打印
- 周期定时器中断
- PWM 输出
- ADC 采样
- SPI / I2C 传感器通信
- 简单 DMA 搬运
- 基础非易失存储或可移除存储

不要把高级特性当成中心前提。

## 不要做什么

- 不凭文件名下结论。
- 不把自动生成配置当唯一真相。
- 不在没跑通前先重构。
- 不先换架构再看问题。
- 不把临时绕过方案当最终方案。
- 不在未经确认时静默降低要求。
- 不为了“更优雅”增加抽象层。
- 不把多个未验证修改打包在同一次尝试里。

## 适用边界

- 这份 skill 面向通用、基础、保守的 STM32 项目处理方式。
- 不依赖某个具体芯片、某个具体板子、某个具体库。
- 即使任务更复杂，也先从这里的基础检查开始，再逐步上升复杂度。
