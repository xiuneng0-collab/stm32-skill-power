# STM32 Migration

这份 skill 只做一件事：把 STM32 工程迁移这件事拆干净，先保行为一致，再做平台适配。

## 迁移时的默认立场

默认把迁移问题分成两部分：

1. 已验证行为
2. 新平台适配

迁移失败，很多时候不是因为原逻辑不对，而是因为这两部分被混在一起改了。

默认原则：

- 先保原来已经验证过的行为。
- 先找不变量，再找适配点。
- 先迁移，再优化。
- 先最小跑通，再谈重构。

## 先确认什么

开始迁移前，先确认下面这些事实：

### 1. 旧工程里什么是真的

- 哪些功能已经跑通
- 哪些参数、速率、时序、链路已经验证
- 哪些只是目录名、注释名、旧命名，不一定可信

### 2. 新工程是什么底子

- 只是空骨架
- 还是已经带部分外设配置
- 还是已经做过一轮手改

### 3. 用户真正要保什么

- 业务行为一致
- 采样、通信、存储、控制逻辑一致
- 只是能编译，还是必须真实运行一致

## 迁移时先拆层

默认按下面层次拆分：

### 可以优先复用的层

- 主流程逻辑
- 状态机
- 数据处理
- 协议封装
- 业务判断

### 必须重新核对的适配层

- 时钟
- GPIO 与复用
- 中断号与中断入口
- DMA 实例与通道
- 内存映射
- 外设实例
- 板级宏定义
- 中间层胶水代码

### 最容易被漏掉的中间层

- MSP
- 板级头文件
- USB / FATFS / 存储接口适配层
- 驱动回调
- 条件编译宏
- 工程文件里的源文件列表

## 标准迁移顺序

默认按这个顺序推进：

### 1. 提取旧工程不变量

先列出来：

- 哪些行为必须保留
- 哪些参数必须等价
- 哪些特征绝不能静默退化

### 2. 核对新平台基础资源

- 时钟结构
- 可用引脚
- 外设实例
- 中断与 DMA 资源
- 板级连接事实

### 3. 先迁业务层，再补适配层

不要先把新平台底层“美化”到自认为完美，再去接旧逻辑。

更稳的顺序是：

- 先把旧逻辑带过来
- 再让它适应新平台
- 再修编译与运行连接处

### 4. 只改必要层

如果问题只是：

- 外设名称不同
- 引脚不同
- 时钟不同
- 中断号不同
- 存储基地址不同

那就只改这些层，不要顺手改业务逻辑。

### 5. 分阶段验证

迁移不要一次性验证所有功能。

默认分阶段：

1. 能编译
2. 能启动
3. 最小观测点正常
4. 单链路正常
5. 全链路正常

## 迁移时最常见的错误

### 1. 被旧名字误导

旧工程目录名、文件名、宏名不一定代表真实功能。

默认相信：

- 当前源码路径
- 当前运行行为
- 当前资源使用

而不是旧命名。

### 2. 把“平台差异”当成“逻辑差异”

例如：

- 时钟变了
- 引脚变了
- DMA 变了
- 中断入口变了

这通常是适配问题，不是功能逻辑问题。

### 3. 只拷主文件，不拷中间层

很多迁移失败不是主逻辑错，而是：

- 存储接口层还是占位实现
- USB 中间层没带过来
- 驱动回调没带过来
- 工程文件没把源文件编进去

### 4. 在迁移时顺手升级功能

迁移期默认不要：

- 换架构
- 换缓冲模型
- 换状态机
- 换总流程

除非旧方案在新平台上根本不成立。

## 迁移排查模板

如果迁过去后不工作，默认按这个顺序排查：

### 编译不过

先查：

- 头文件
- 工程文件源文件列表
- 条件编译
- HAL 模块开关
- 中间层漏文件

### 编译过了但启动不对

先查：

- 启动文件
- 时钟
- GPIO 基础配置
- 最早期观测点

### 启动正常但功能不对

先查：

- 引脚复用
- 外设实例映射
- 中断与 DMA 映射
- 板级连接与旧工程假设是否一致

### 单模块正常但全链路不对

先查：

- 初始化顺序
- 缓冲区所有权
- 中间层胶水
- 资源冲突

## 输出模板

处理 STM32 迁移任务时，尽量按这个顺序输出：

### 已确认的不变量

- 哪些行为必须保

### 新平台适配点

- 哪些地方必须改

### 可以直接复用的部分

- 哪些逻辑先不动

### 最小迁移路径

- 先迁什么
- 后迁什么

### 验证顺序

- 先看编译
- 再看启动
- 再看单链路
- 最后看全链路

## 不要做什么

- 不要因为名字像就直接复制结论
- 不要把迁移和重构绑在一起
- 不要上来先优化新平台
- 不要无声降低旧行为要求
- 不要主文件迁了就以为工程迁完了
